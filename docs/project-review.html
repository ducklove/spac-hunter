1.요약 및 종합 평가

스팩 헌터는 국내 코스닥 상장 스팩 73종목을 「현재가/공모가」 중심으로 추적하는 정적 대시보드입니다. KRX·KIND·DART·네이버증권·KOFR 5개 소스를 스크래핑하는 파이썬 파이프라인(fetch_data.py)이 매일 GitHub Actions 크론으로 실행되어 data.js(현재 1.8MB)를 저장소에 커밋하고, 빌드 과정 없는 단일 index.html이 이를 읽어 렌더링합니다.

도메인 설계(청산분배금·연환산 수익률 계산, 합병 공시 분류, 이벤트별 가격 반응 추적)는 수준이 높고 차별화된 가치가 있습니다. 반면 엔지니어링 기반은 빈약합니다 — 테스트가 0개이고, 운영 데이터를 샘플 데이터로 덮어쓸 수 있는 폴백 경로와 운영 환경에서 보정 레이어(overrides.json)가 무력화되는 구성 오류 등 치명도 높은 이슈 2건(P0)이 존재합니다. 리팩토링은 "구조 개선"보다 "안전망 구축(Phase 0)"을 먼저 수행해야 합니다.

아키텍처 평가

"스크래핑 결과를 저장소에 커밋하고 정적 페이지로 서빙"하는 구조는 서버·DB 비용 0원, file://로도 동작, 데이터 변경 이력이 git에 남는 합리적인 선택입니다. 특히 data.js를 <script>로 읽는 방식은 CORS 없이 로컬에서 열리는 장점이 있습니다. 이 기본 구조는 유지할 가치가 있으며, 리팩토링은 이 구조를 깨지 않는 방향으로 설계했습니다. 다만 두 가지 구조적 부채가 있습니다:

  • 데이터 파일 무한 성장 — 73종목 × 매일 1포인트씩 히스토리가 누적되어(현재 12,082포인트·평균 165개/종목·최대 719개) data.js가 연 1MB 이상씩 커집니다. 단일 블로킹 스크립트(index.html:1292)라 초기 로딩이 선형으로 느려집니다.
  • git 히스토리 오염 — 최근 커밋의 절반이 "Update SPAC data"입니다. 데이터와 코드의 이력이 섞여 코드 리뷰·블레임이 어려워집니다.

3.3 CI — .github/workflows/pages.yml

배포·데이터 갱신·커밋이 하나의 워크플로에 결합되어 있습니다. 크론(18:10 KST) 또는 수동 실행 시 fetch_data.py를 돌려 변경분을 main에 커밋한 뒤 Pages로 배포합니다. 린트·테스트 잡은 없으며, 수집 실패 시 알림 수단이 없습니다(Actions 실패 메일에만 의존). requirements.txt는 pykrx만 버전 고정이고 pandas·requests·beautifulsoup4는 미고정이라 pandas 메이저 업데이트 시 파이프라인이 깨질 수 있습니다.

4.품질 평가 — 강점

  • 다층 폴백 체인 — KIND 실패→DART, 네이버 히스토리 실패→pykrx, KOFR 실패→0% 보수적 금리, KIND 법인목록 실패→기존 데이터 재사용. 개별 소스 장애에 강합니다.
  • 히스토리 보존 병합 — merge_history_points/merge_merger_price_records가 기존 data.js를 읽어 새 수집분과 날짜 키로 병합. 수집 창이 짧아도 과거 데이터가 유지됩니다.
  • 방법론의 투명성 — 산출물에 methodology·rateAssumption·sourceLinks 메타데이터를 포함시켜 모든 수치의 가정을 추적할 수 있습니다. 금융 데이터 도구로서 신뢰성의 핵심.
  • 합병 에피소드 상태기계 — 신청→확정/철회를 에피소드 단위로 묶어 성사 확률·소요 기간을 산출하는 설계(build_merger_episodes)는 단순 공시 나열보다 한 단계 높은 분석입니다.
  • 프런트 보안 습관 — 동적 삽입 전부 escapeHtml 경유, localStorage 접근 try/catch, rel="noopener".
  • UX 디테일 — 다크 테마, iframe 임베드 모드, ?code= 딥링크+popstate 처리, 정렬 가능 테이블, 반응형 레이아웃.
  • 무비용 운영 — 서버리스 정적 구조 + 일일 자동 갱신으로 유지비 0원.

P0 overrides.json이 운영(CI)에서 전혀 적용되지 않음 .gitignore:4에 등록되어 저장소에 없고 워크플로도 생성하지 않음. 공모가·실제 청산일·확정 분배금 보정이라는 "핵심 수동 레이어"(README)가 로컬 실행에서만 동작. 로컬에서 보정해 커밋해도 다음날 크론이 보정 없는 데이터로 덮어씀. 민감정보가 아니므로 overrides.json을 저장소에 커밋(gitignore 해제). 또는 Actions secret/variable로 주입.
P1 테스트 0개 + 품질 게이트 부재 5개 외부 소스의 HTML 구조에 의존하는 파서가 회귀 검증 없이 운영 중. 파서가 빈 결과를 내도 "0건 수집 성공"과 구분 불가. 순수 함수(파싱·분류·통계)부터 pytest 도입, 파서는 HTML 픽스처 고정. CI에 ruff+pytest 잡 추가. (Phase 1)
P1 공모가 기본값 2,000원 하드코딩 DEFAULT_IPO_PRICE = 2000(fetch_data.py:30). 현재 73종목 전부 2,000원이라 표면화되지 않았지만, 공모가 1만원 스팩(과거 대형 스팩 전례 있음) 상장 시 비율·괴리·기대수익률이 5배 왜곡. P0-②와 결합되면 보정 수단도 없음. OpenDART 증권신고서에서 공모가 자동 수집(7장 기능 ①), 단기적으로는 overrides 운영 정상화로 커버.
P1 data.js 무한 성장 + 동기 로딩 1.8MB·12,082포인트, 연 1MB+ 증가 추세. <script src="data.js">가 블로킹이라 파싱 비용이 매일 증가. 모바일 첫 로딩 저하. 코어(시세·요약·통계)와 종목별 히스토리 분리, 히스토리는 선택 시 lazy fetch. (Phase 3)
P1 pykrx 내부(private) API 의존 from pykrx.website.krx.market import core; getattr(core, "상장종목검색")(fetch_data.py:188-191) — 문서화되지 않은 내부 모듈 경로. pykrx==1.2.4 고정으로 버티는 중이나 유니버스 수집(파이프라인의 시작점)이 단일 장애점이며, 실패 시 P0-① 경로 발동. KRX 정보데이터시스템 공식 OTP API 직접 호출로 교체하거나 pykrx 공개 API(stock.get_market_ticker_list) 사용.
P2 모놀리스 2개 (1,684줄 / 2,161줄) 수집·도메인·통계·출력·CLI가 한 파이썬 파일, CSS·마크업·JS가 한 HTML 파일. 변경 영향 범위 파악과 부분 테스트가 어려움. 6장 목표 구조로 점진 분리. 동작 변경 없이 이동만 먼저.
P2 예외 처리·로깅 비일관 except Exception 18곳(전부 noqa: BLE001), fetch_naver_history는 페이지 실패를 조용히 skip. 로깅은 print. errors 구조도 dict/str 혼재. logging 도입, 소스별 수집 성공률을 구조화해 payload에 포함, 실패 유형별 예외 구분.
P2 수집 오류·데이터 신선도가 UI에 미노출 payload의 errors를 프런트가 전혀 사용하지 않음. 크론이 며칠 멈춰도 사용자는 lastUpdated를 직접 읽어야 인지 가능. lastUpdated가 36시간 초과 시 경고 배너, errors 요약 토글 표시.
P2 전체 재렌더 + 리스너 재바인딩 renderCards/renderTable이 호출될 때마다 innerHTML 재생성 후 모든 행에 addEventListener(index.html:1745, 1998). 검색 디바운스 없음. 리스트·테이블 컨테이너에 이벤트 위임 1회 바인딩, 검색 input 150ms 디바운스.
P2 KIND 공시 페이지네이션 없음 currentPageSize: 30, pageIndex: 1 고정(fetch_data.py:307-308) — 검색어당 30건 초과 공시는 누락. 상장 4년차 스팩이면 도달 가능. totalCount 파싱 후 2페이지까지 순회.
P2 합병 취소 토큰 "철회"의 과잉 매칭 MERGER_CANCEL_TOKENS에 단독 "철회" 포함(fetch_data.py:55-61) — 합병과 무관한 "신고 철회"류 공시도 상태를 리셋시킬 수 있음. "합병"과의 결합 조건 또는 제목 컨텍스트 검사 추가. 분류 함수 테스트 케이스에 포함.
P3 테마 전환 시 시장통계 차트 색상 미갱신 (버그) 테마 버튼이 drawChart()만 다시 호출(index.html:2087-2093) — belowTrendChart는 창 리사이즈 전까지 이전 테마 색으로 남음. drawBelowTrendChart() 호출 추가 (1줄 수정).
P3 "화면 갱신" 버튼이 재렌더만 수행 data.js를 다시 받지 않으므로 이름과 달리 새 데이터를 가져오지 않음(index.html:2094-2096). fetch('current.json?ts=...')로 시세 핫 리로드하거나 버튼 명칭 변경.
P3 일일 데이터 커밋의 git 오염 커밋 이력의 절반이 "Update SPAC data". 코드 diff 추적성 저하. 데이터를 data 브랜치로 분리하거나 Pages 아티팩트 단계에서만 생성(단, 히스토리 병합 원본 확보 방법 함께 설계 — Phase 3).
P3 의존성 미고정 · LICENSE 부재 pandas 등 3개 패키지 버전 미지정. 공개 저장소임에도 라이선스 없음(법적으로 all rights reserved). requirements.txt 버전 고정(또는 lock 파일), MIT 등 라이선스 추가.
P3 스크래핑 운영 리스크 네이버·KIND·DART 비공식 엔드포인트 사용. 차단·구조 변경은 통제 불가 영역. OpenDART 공식 API(무료 키) 전환으로 의존도 축소, 요청량 보수적 유지(현재도 양호).

6.리팩토링 로드맵 (Phase 0~3)

원칙: ① 안전망 먼저, 구조는 나중 ② 무빌드 정적 아키텍처는 유지 ③ 각 Phase는 독립적으로 배포 가능하고 동작 동일성을 보장.

Phase 0 — 안전망 구축 최우선 예상 반나절~1일

  1. 샘플 폴백 차단: 라이브 수집 실패 시 sys.exit(1)로 종료(데이터 미기록). --sample 명시 시에만 샘플 작성. 워크플로 실패는 그대로 노출.
  2. 커밋 가드: write_outputs 전 검증 — 신규 spac 수가 기존의 70% 미만이거나 시세 수집 성공률이 50% 미만이면 중단. (별도 validate_data.py로 CI에서도 재검증)
  3. overrides 운영 정상화: .gitignore에서 제거하고 저장소에 커밋. 예시 파일과 병합 규칙은 README에 명시.
  4. 의존성 고정: requirements.txt에 상한 포함 버전 명시.
  5. 1줄 버그 수정: 테마 전환 시 drawBelowTrendChart() 재호출.

7.추가 기능 제언

① 지금 바로 — 가치 높음 · 비용 낮음

  • 스폰서(주관사)별 합병 성사율 통계 — sponsor와 에피소드 데이터를 이미 보유. 집계 함수 1개 + 통계 패널 1개로 "어느 증권사 스팩이 합병을 잘 시키는가"라는 차별화 지표 제공.
  • 테이블 행 스파크라인 — 히스토리 데이터 보유, 30×8px 캔버스로 추세 한눈에.
  • CSV 내보내기 — 현재 필터·정렬 상태의 비교 테이블을 Blob 다운로드.
  • 금리 시나리오 슬라이더 — 청산분배금이 (1+r)^t 수식이므로 클라이언트에서 r만 바꿔 재계산 가능. 재수집 불필요.

② 다음 분기 핵심 — 가치 높음 · 비용 중간

  • OpenDART API 전환·보강 (README 로드맵 ①) — 무료 API 키로 증권신고서에서 실제 공모가·예치금·예치이율·공모주식수를 수집. P1 "공모가 하드코딩"과 기대수익률 정확도를 근본 해결. 해산사유 발생 공시로 청산 진행도 자동 감지.
  • 가격 알림 봇 — 크론 후 조건 평가(예: ratio < 0.99 진입, 합병 신청/확정/철회 발생) → Telegram Bot API 또는 RSS 피드 파일 생성. 정적 구조 그대로 유지 가능.
  • 청약·상장 캘린더 탭 (README 로드맵 ②) — KIND 공모일정에서 스팩 청약/납입/상장 수집, 월간 캘린더 뷰.
  • 워치리스트 — localStorage 기반 별표 + 보유수량 입력 시 포트폴리오 기대 청산수익 합산.

③ 차별화 투자 — 가치 높음 · 비용 높음

  • 합병 대상 기업 패널 — 공시 제목·본문에서 대상기업명, 합병비율, 주식매수청구권 행사가를 파싱. 스팩 차익거래에서 매수청구가는 사실상의 하방 보호선이라 실투자 가치가 매우 큼.
  • 상폐(합병 완료) 스팩 아카이브 — 현재 통계는 상장 중 종목만 모수(코드 내 note도 한계 명시). 합병 상장으로 사라진 스팩을 보존해 성사율·수익률 통계의 생존 편향 제거.
  • 전략 백테스트 — "공모가 이하 매수 → 청산/합병까지 보유" 실현 수익률 분포. 아카이브가 선행 조건.

④ 선택 — 가치 보통

  • PWA(매니페스트+오프라인 캐시), 다중 종목 비교 차트 오버레이
  • current.json을 공개 데이터 API로 문서화 (이미 CORS 가능한 정적 파일)
  • 영문 토글(i18n), 공시 원문 뷰어 모달
추천 우선순위 Phase 0(안전망) → ①스폰서 성사율 + 금리 슬라이더(빠른 가치) → Phase 1(테스트 기반 확보) → ②OpenDART 전환(정확도의 근본 개선) → ②가격 알림(사용 빈도를 만드는 기능) 순. OpenDART 전환은 P0-②·P1 공모가 이슈·스크래핑 리스크를 동시에 줄이는 레버리지가 가장 큰 단일 투자입니다.

8.향후 방향 시나리오

시나리오내용투자판단
A. 개인 도구 유지 Phase 0만 수행하고 현 구조 동결. 본인 투자 판단용으로만 사용. ~1일 최소한 Phase 0은 필수 — 현재는 데이터 소실 리스크를 안고 운영 중.
B. 공개 대시보드 강화 추천 Phase 0~3 + 기능 ①·② 수행. "국내 스팩 데이터의 기준점" 포지셔닝. 정적·무비용 구조 유지. 2~4주 (파트타임) 국내에 스팩 전문 무료 대시보드가 드물어 틈새 가치가 분명. 현 아키텍처 연장선이라 리스크 낮음. 단, 공개 서비스화 시 투자 조언이 아니라는 면책 문구와 데이터 출처·지연 고지 필요.
C. 서비스화 백엔드(DB·계정·실시간 알림·푸시) 도입. 수개월+ 운영비 현 단계 비추천 — B의 알림 봇·워치리스트로 핵심 수요의 80%를 무비용으로 충족 가능. B에서 사용자 반응 확인 후 재검토.
